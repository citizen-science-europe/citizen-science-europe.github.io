# FreWA full build prompt

Build and deploy a working freshwater observation website called **FreWA**.

What we want to demonstrate is: someone completes the full questionnaire on their phone, the observation is saved to a central server, and another person sees it appear automatically on a shared map.

Everything needed to implement the questionnaire is written below. Treat this specification as authoritative. Include all 20 main question groups, their answer options, the Other water-use text field, and the conditional turbidity result field. Do not simplify the questionnaire or change scientific categories.

### 1. Implementation and deployment

Use the hosting, database, and development tools available in your environment. Check access to persistent storage and public deployment early. Make routine implementation decisions and proceed through building, testing, and deployment where tools permit.

Deliver a publicly accessible HTTPS URL with a working server API, persistent shared database, and persistent photograph storage. Records must survive browser closure and be available from another browser or device.

If a required capability or account connection is unavailable, state the specific missing access, complete the work that is possible, and provide the remaining setup steps. Never describe a local preview or device-only store as a working shared deployment. Keep credentials and privileged database access on the server.

State the services used and their known costs or limits. Do not assume hosting or AI access is free. Do not activate a paid service without approval. The completed application should not require an AI API to collect or display observations.

### 2. Questionnaire and validation

Use the sections, labels, field identifiers, answer options, and rules below. Keep identifiers stable in the data model and exports.

Only **site name, latitude and longitude, observation date, and freshwater body type** are required. **Observation time is optional.** All other questions are optional, subject to the conditional validation specified below.

New forms should be blank except that the observation date may default to today's local date. Leave time and environmental answers unselected. Do not populate example coordinates, results, participant counts, notes, or photos in a new observation.

#### General information

**G1. Site name**

- Control: single-line text.
- Required: yes.
- Reject an empty or whitespace-only value.

**G2. Geolocation**

- Controls: latitude and longitude in decimal degrees, WGS84.
- Required: both coordinates.
- Provide a “Use my location” button that requests permission when selected.
- Offer manual coordinate entry when permission is declined, location capture fails, or the observer needs to identify a different sampling location.
- Display the coordinates and let the observer confirm the intended sampling location before submission.
- Validate latitude from −90 to 90 and longitude from −180 to 180. Accept valid zero values.
- Do not substitute a default site when location capture fails.

**G3. Sample date and time**

- Controls: a date picker and a separate optional time control.
- Date: required, editable, may default to today's local date.
- Time: optional, blank by default.
- Store observation date as YYYY-MM-DD and observation time as a nullable HH:mm value. Keep the relevant time-zone context when a time is supplied.
- A date-only observation must save successfully and display and export with its time blank.
- Never fill a missing observation time with midnight, device time, or the server's receipt time.
- Record the server's receipt timestamp separately as submission metadata.
- Only derive a complete observation timestamp when the date, time, and time-zone context are available. Preserve the original local date and time.

**G4. Image**

- Control: optional photograph.
- Offer “Choose an image” and “Take a photo” where supported by the device.
- Show a preview and allow removal or replacement before submission.
- Store the uploaded photograph persistently and associate it with the observation. Include its reference in the saved record and export.
- State supported file types and size limits and show a clear error for an unsupported upload.

**G5. Total number of participants**

- Control: optional whole number.
- If entered, the value must be at least 1.
- Keep an unanswered value empty, rather than treating it as zero or one.

**G6. Notes**

- Control: optional multiline text.

#### Ecological

**E1. Freshwater body type**

- Control: single selection.
- Required: yes.
- Options:
  - Pond
  - Stream
  - Lake
  - River
  - Wetland
  - Other

**E2. What is the land use in the immediate surroundings?**

- Control: optional single selection.
- Options:
  - Urban residential
  - Industrial
  - Urban park
  - Agriculture
  - Forest
  - Grassland/shrub
  - Other

**E3. What is the bank vegetation? Select all that apply.**

- Control: optional multiple selection.
- Options:
  - Trees/shrubs
  - Grass
  - No vegetation cover
  - Other
- “No vegetation cover” is exclusive of the other answers in this question.

**E4. Is there any of the following on the water surface?**

- Control: optional multiple selection.
- Options:
  - None
  - Foam
  - Floating algae
  - Litter
  - Oily film
- “None” is exclusive of the other answers in this question.

**E5. Are there any pollution sources in the immediate surrounding area? Select all that apply.**

- Control: optional multiple selection.
- Options:
  - Industrial discharge
  - Residential discharge
  - Urban/road discharge
  - Other
- Display these as observer-reported observations. Do not present a selection as verification of a pollution source.

**E6. Can you see evidence of the following water uses? Select all that apply.**

- Control: optional multiple selection.
- Options:
  - Fishing
  - Swimming
  - Boating
  - Irrigation
  - Public water supply
  - Other

**E6_OTHER. Other**

- Control: optional text explanation.
- Show when “Other” is selected in E6.
- Retain the entered explanation in the saved record and export.
- Treat this as an additional field within E6.

**E7. What aquatic life is there evidence of? Select all that apply.**

- Control: optional multiple selection.
- Options:
  - Plants below the surface
  - Plants emerging from the water
  - Floating plants
  - Fish
  - Frogs/toads
  - Aquatic birds
  - None
  - Other
- “None” is exclusive of the other answers in this question.

**E8. Algae appearance: select all that apply.**

- Control: optional multiple selection.
- Options:
  - No algae
  - Evenly dispersed
  - Floating mats
  - Attached
  - Blue-green scum
- “No algae” is exclusive of the other answers in this question.

#### Hydrological

**H1. Estimate the water flow**

- Control: optional single selection.
- Options:
  - Surging
  - Steady
  - Slow
  - Still

**H2. Estimate the water level**

- Control: optional single selection.
- Options:
  - High
  - Average
  - Low

#### Chemical

The nutrient kit is **FreshWater Watch**. Units are **ppm**. Nitrate results are reported **as nitrogen (N)**; phosphate results are reported **as phosphorus (P)**.

Keep the kit, units, and reporting basis visible in the form, record details, and exports. Store them as measurement metadata without requiring the observer to re-enter them.

**C1. Nitrate (ppm as nitrogen, N)**

- Control: optional single selection.
- Method/kit: FreshWater Watch kit.
- Analyte: nitrate.
- Reporting basis: nitrogen (N).
- Unit: ppm.
- Options:
  - `<0.2`
  - `0.2–0.5`
  - `0.5–1`
  - `1–2`
  - `2–5`
  - `5–10`
  - `>10`

**C2. Phosphate (ppm as phosphorus, P)**

- Control: optional single selection.
- Method/kit: FreshWater Watch kit.
- Analyte: phosphate.
- Reporting basis: phosphorus (P).
- Unit: ppm.
- Options:
  - `<0.02`
  - `0.02–0.05`
  - `0.05–0.1`
  - `0.1–0.2`
  - `0.2–0.5`
  - `0.5–1`
  - `>1`

For both nutrient questions, preserve the selected category, including decimal places, inequalities, and range boundaries. Do not replace a range with its midpoint or convert the reporting basis to nitrate as NO3 or phosphate as PO4. Unanswered results remain empty.

#### Optical

**O1. Water quality: Secchi tube (turbidity), NTU**

- Control: optional single selection.
- Method: Secchi tube.
- Measurement: turbidity.
- Unit: NTU.
- Options:
  - `<14`
  - `>240`
  - Enter result
- When “Enter result” is selected, show a numeric result input labelled NTU.
- Require a finite, non-negative numeric result only when “Enter result” is selected.
- Store the selection and numeric result separately. Selecting <14 or >240 must leave the numeric result empty.
- Preserve threshold categories as written. Do not turn <14 into a measured value of 14 or >240 into a measured value of 240.
- Do not convert the result into water depth or a drinking-water safety assessment.

**O2. Estimate the water colour**

- Control: optional single selection.
- Options:
  - Colourless
  - Yellow
  - Brown
  - Green
  - Other

#### Shared field rules

- Provide a way to clear an optional single selection.
- Preserve all selected answers for multiple-selection fields.
- Enforce exclusive “None”, “No algae”, and “No vegetation cover” choices within their respective questions.
- Preserve the distinction between an unanswered question, a valid zero, and an explicit absence such as “None”.
- Use “Not recorded” when displaying a missing answer; keep the underlying value empty.
- Do not add answer options, extra mandatory questions, scientific scores, or inferred measurements.
- Validate submissions on the server as well as in the form.
- If a conditional choice changes, prevent a stale hidden answer from being submitted as an active result.

### 3. Save observations and handle interrupted connectivity

Implement a server API and persistent shared database containing every questionnaire field and the measurement metadata above.

Assign each observation a stable unique identifier before the first upload attempt. Retrying the same observation must not create a duplicate.

Store pending observations and any selected photograph on the device until the server confirms their receipt. Retry when connectivity returns while the application is open. A successful local save is “Pending upload”; show “Saved to server” only after server acknowledgement.

Show clear pending, uploading, saved, and failed states. Keep answers available after a failed attempt and offer a retry action. Show the status of photograph uploads so an observation is not described as fully uploaded while its image is still pending.

Document limits involving closing the application, offline reopening, background syncing, browser storage, and photo uploads. Do not promise offline behaviour that has not been implemented and tested.

### 4. Shared map, records, and exports

Provide:

- An interactive shared map with selectable observation markers.
- A records table linked to the same database.
- A record details view showing every recorded answer and the photograph, if present.
- Date and location filters.
- CSV export covering every questionnaire field, additional conditional field, measurement method, unit, reporting basis, photograph reference, and observation identifier.
- Separate observation date, optional observation time, time-zone context where available, and server receipt timestamp in storage and exports.

Automatically refresh shared observations, aiming for new submissions to appear within five seconds under normal connectivity. Use a suitable polling or real-time mechanism.

Make skipped answers and date-only observations display clearly. Date filters must work when the observation time is missing.

Use consistent CSV headers, proper CSV escaping, and a documented representation for multiple selections. Preserve categorical nutrient ranges and turbidity thresholds without converting them to single numbers. Include all saved fields even when they are empty.

### 5. Experience

Use a clean, accessible layout that works on phones and desktop screens. Keep labels readable, tap targets usable, and validation messages beside the affected controls. Group questions by their survey sections and preserve entered answers when moving between sections.

Make the demonstration publicly viewable and permit anonymous test submissions. Restrict editing and deletion of shared records to an authenticated owner. Hiding an edit button alone is insufficient; enforce access on the server.

Use synthetic observations and non-identifying sample photographs for testing. Clearly label any seeded examples as demonstration data. Keep seeded examples separate from blank new-observation forms.

Keep the first version focused on collection, server storage, the shared map, and exports. Leave external dataset imports, connections to other platforms, and additional features for later prompts. Use documented field identifiers and export formats so later integration is practical.

### 6. Test the completed workflow

Run checks against the working implementation and report each as **passed**, **failed**, or **not tested**, with concise evidence. Fix observed failures where possible.

Check that:

1. All 20 main question groups, every listed option, E6_OTHER, and the conditional numeric turbidity input appear where specified.
2. Every field and measurement detail is preserved in saved records, record details, and CSV export.
3. Site name, valid latitude and longitude, observation date, and freshwater body type are required.
4. An otherwise valid observation with no time submits successfully, persists, appears on the map, and exports with its time blank.
5. Optional questions can remain unanswered. Exclusive absence choices cannot coexist with contradictory selections in the same question.
6. Nutrient categories retain their original ranges and inequalities, with the FreshWater Watch kit, ppm, and N/P reporting bases retained.
7. All three turbidity choices work. “Enter result” requires a valid number; threshold choices do not fabricate a numeric measurement.
8. A submission persists after refresh and is visible in a separate browser session or device.
9. Another session's map and table update automatically after a submission, with the observed refresh delay reported.
10. Coordinates place the marker correctly, and date and location filters return the expected records.
11. An observation submitted without connectivity uploads after reconnection while the app is open, with no duplicate from repeated retries.
12. An optional photograph persists and remains linked to its observation, including after a retry.
13. Anonymous users can view and submit demo observations; unauthorised requests to edit or delete shared records are rejected.
14. The form, map, records, and export work at phone and desktop widths.

Do not report a check as passed based only on reading the code. Distinguish implemented behaviour from behaviour verified in a running application.

### 7. Deliver

Provide:

- The working public HTTPS URL, or the precise deployment blocker and remaining steps.
- Editable application source and the steps needed to run and redeploy it.
- A field-coverage checklist mapping each questionnaire identifier to its form control, stored field, and export column.
- Test results, unresolved failures, and untested behaviour.
- A short explanation of how observations travel from phone to central database to shared map.
- Services used, known costs or usage limits, and connectivity limitations.

Complete the implementation and available deployment steps. Make the first working version suitable for a workshop demonstration, with participants refining it through follow-up prompts.
